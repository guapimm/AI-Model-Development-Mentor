# Правила рабочего процесса разработки

## 1. Инициализация проекта и система документации

### Лёгкий режим (объём кода < 500 строк)
Достаточно только `README.md`, включающего: краткое описание проекта, технологический стек, основные структуры таблиц, список интерфейсов, шаги развёртывания.

### Стандартный режим (объём кода ≥ 500 строк)
При запуске проекта создавать следующую структуру документов:

```
📁 /docs/
├── architecture.md      # Обоснование выбора технологического стека (с бытовыми аналогиями), схема архитектуры системы (Mermaid), структура каталогов
├── dev_log.md           # Журнал разработки: время, изменения, результаты тестов, известные проблемы и их решения
├── api_interface.md     # Контракты интерфейсов фронтенда и бэкенда (URL, параметры, возвращаемые значения, сценарии исключений)
└── SNAPSHOT.md          # Ключевой снимок (≤200 строк): версии технологического стека, список таблиц, пути API, схема бизнес-процесса
```

Оптимизация Token: в конце каждого диалога формируйте 【Сводку контекста】（прогресс, имена переменных, задачи, пароль для продолжения）.

## 2. Протокол визуального позиционирования фронтенда

Перед написанием фронтенд-кода сначала выводите следующую информацию о позиционировании:

### 1. Схема макета страницы
Используйте ASCII-каркас или Mermaid-дерево компонентов, чтобы чётко задать структуру страницы.

### 2. Таблица сопоставления UI-элементов

| Визуальное расположение | Имя компонента | Соответствующий путь к файлу | CSS-класс/ID | Описание функциональности |
|---------|---------|------------|------------|---------|
| Правая часть верхней навигационной панели | UserAvatar | /src/components/Header.tsx | .user-avatar | Аватар пользователя и выпадающее меню |

### 3. Таблица сопоставления событий фронтенда

| Название | Действие | Вызываемый бэкенд-интерфейс | Ожидаемый результат |
|-------|------|------------|---------|
| Кнопка «Войти» | Клик | POST /api/login | Переход на главную страницу, сохранение Token |

## 3. Механизмы развёртывания и аварийного восстановления

### Локальное резервное копирование
- Предоставьте скрипт резервного копирования в один клик `backup.sh`, экспортирующий код + конфигурацию + базу данных в `./local_backup/`
- Перед каждым развёртыванием проверяйте наличие локальной резервной копии, иначе — отказывайте в развёртывании

### Серый откат на облачном сервере
- Перед развёртыванием нового кода автоматически упаковывайте старую версию в `backup_временная_метка.zip`
- Экстренный откат в три шага:
  1. `./rollback.sh latest` — распаковать последнюю резервную копию
  2. `docker-compose restart` (или `pm2 restart all`)
  3. `./health_check.sh` — вывести статус сервиса
- Фиксируйте в `dev_log.md` время резервного копирования, пути и записи об откате

### Изоляция окружений
- Разделяйте конфигурации окружений разработки и production
- Заранее подсказывайте пункты конфигурации безопасности, которые нужно изменить для production

## 4. Расширение требований и предложения

После завершения заданной пользователем функции выводите «Карточку предложений по улучшению функции»:

- ✅ **Итог завершённых функций** — чётко описать, какие функции доступны в данный момент
- 🔮 **Предупреждение о потенциальных рисках** — параллельный доступ, согласованность данных, зависимости от третьих сторон и т. п.
- 🚀 **Рекомендуемые функции для расширения** — помечать приоритет P0/P1/P2, уровень сложности ⭐, ожидаемый эффект
- ⚠️ **Гайд по граблям для новичков** — частые заблуждения, меры предосторожности

## 5. Замкнутый цикл тестирования и самопроверки

### Минимальный проверяемый тестовый сценарий
Предоставляйте шаги проверки, которые пользователь может выполнить вручную, например:
> «Нажмите кнопку входа, введите правильные логин и пароль, проверьте успешный переход на главную страницу»

### Заявление о логической самосогласованности
После вывода кода обязательно заявляйте:
> «Я проверил: ① области видимости переменных корректны ② асинхронная обработка полная ③ перехват исключений покрыт ④ нет утечки чувствительной информации ⑤ нет явных узких мест производительности»
